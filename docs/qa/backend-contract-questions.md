# پرسش‌ها و درخواست‌های تیم بک‌اند برای انتشار فیچر ۱

## هدف و وضعیت فعلی

این یادداشت برای تعیین قراردادهای موجود است، نه درخواست بازنویسی بک‌اند. اگر تضمین یا endpoint لازم از قبل وجود دارد، مسیر، نسخه قرارداد و نمونه پاسخ ساختگی آن کافی است.

در فرانت، محافظ چرخه عملیات حساب، انتقال لغو درخواست، deadline راه‌اندازی نشست و پاک‌سازی تب authenticated هنگام دریافت پیام ورود جایگزین اصلاح شده‌اند. تست‌های رگرسیون نوشته شده‌اند، اما اجرای آن‌ها و build این مرحله هنوز تأیید نشده است.

**تولید تصویر/ویدیو، پرداخت یا ارسال OTP واقعی انجام نشده است. همه سناریوهای پذیرش زیر باید با provider/درگاه ماک، حساب آزمایشی و دفتر مالی آزمایشی اجرا شوند؛ بدون کسر اعتبار واقعی.**

## ۱. اولویت انتشار: نتیجه نامعلوم تولید هزینه‌دار

### آنچه فرانت از قرارداد فعلی می‌بیند

`POST /api/v1/ai-task/generate` این داده‌ها را می‌گیرد:

```json
{
  "ai_model_uuid": "<model UUID>",
  "task_type": "IMAGE or VIDEO",
  "ai_model_config": {},
  "task_uuid": "<existing conversation UUID or omitted>"
}
```

در OpenAPI موجود، برای این عملیات `Idempotency-Key` یا شناسه عملیات مجزایی اعلام نشده است. `clientAttemptId` فعلی فقط شناسه وضعیت خوش‌بینانه UI است و به سرور فرستاده نمی‌شود. `task_uuid` نیز شناسه گفتگو است و به‌تنهایی هویت یک تولید مجزا را مشخص نمی‌کند.

### پاسخ لازم از بک‌اند

1. آیا همین endpoint در حال حاضر در برابر retry پس از قطع پاسخ idempotent است؟ دقیقاً با چه کلید و در چه محدوده‌ای؟
2. اگر کلید عملیاتی پشتیبانی می‌شود، در کدام header/body قرار می‌گیرد؟ نوع، scope مالک حساب، مدت نگهداری و رفتار reuse آن چیست؟
3. تکرار کلید با همان payload چه پاسخی می‌دهد؟ آیا همان task/message و همان نتیجه مالی را برمی‌گرداند؟
4. استفاده همان کلید با payload متفاوت چه خطای قراردادی دارد، مثلاً 409؟
5. برای درخواست پذیرفته‌شده با پاسخ گم‌شده، مخصوصاً گفتگوی جدیدی که هنوز `task_uuid` آن به کلاینت نرسیده، endpoint بازیابی وضعیت چیست؟
6. کدام پاسخ‌ها «قطعاً ثبت نشده» هستند و کدام وضعیت‌ها از دید کلاینت نامعلوم‌اند؟ timeout و قطع ارتباط را نمی‌توان خودکار عدم ثبت محسوب کرد.
7. تضمین یکتایی برداشت در ledger چیست؟ آیا retry صف/worker/provider نیز ممکن است عملیات یا برداشت تکراری بسازد؟ refund و شکست جزئی چه وضعیتی دارند؟

### اگر پشتیبانی موجود نیست

قرارداد یک شناسه پایدار برای هر عملیات منطقی و lookup همان عملیات لازم است. retry همان قصد کاربر باید همان شناسه را نگه دارد؛ تولید عمدی جدید باید شناسه جدید داشته باشد. انتخاب نام فیلد/header و سیاست مالی باید از سمت بک‌اند تأیید شود.

فرانت فعلاً header یا فیلد فرضی اضافه نکرده و `clientAttemptId` را به‌جای `task_uuid` نفرستاده است. غیرفعال‌کردن دوباره‌کلیک، یا جستجوی prompt مشابه در تاریخچه، جای تضمین سرور را نمی‌گیرد.

### معیار پذیرش مشترک

- سرور درخواست را بپذیرد؛ پاسخ عمداً قطع شود؛ retry همان عملیات انجام شود.
- دقیقاً یک عملیات منطقی و یک برداشت در دفتر آزمایشی ثبت شود.
- درخواست جدید عمدی با شناسه جدید مستقل اجرا شود.
- وضعیت پس از reload و پاسخ دیررس قابل بازیابی باشد.
- این تست با provider ماک انجام شود، نه مدل پولی واقعی.

## ۲. اولویت انتشار: هویت نشست و جداسازی حساب بین تب‌ها

### آنچه فعلاً داریم

پاسخ ورود/refresh در مدل فرانت شامل `access_token`، `token_type` و `expires_in` است؛ CSRF از header خوانده می‌شود. در `IssuedSession` فعلی شناسه پایدار principal/account یا session family وجود ندارد.

دریافت پیام `session-started` اکنون چرخه و cache قبلی تب را باطل و نشست را دوباره راه‌اندازی می‌کند، بدون ثبت خروج برای ورود جدید. اما اگر تمام اعلان‌ها از دست بروند، فرانت از تغییر مقدار توکن به‌تنهایی نمی‌تواند تعویض حساب را از rotation عادی تشخیص دهد.

### پاسخ لازم

1. آیا refresh/me شناسه پایدار حساب و شناسه خانواده/نسل نشست را ارائه می‌کند؟ نام دقیق فیلد و schema چیست؟
2. آیا access token opaque است یا JWT؟ اگر JWT است، آیا `sub` پایدار و مستند است؟ استفاده کلاینت از claim فقط برای جداسازی cache خواهد بود، نه تصمیم مجوز؛ مجوز همیشه در سرور بررسی می‌شود.
3. اگر فیلد یا claim مناسبی موجود نیست، راه قراردادی تشخیص تعویض حساب پس از refresh چیست؟ آیا باید پاسخ refresh/me تکمیل شود؟
4. سیاست refresh rotation هم‌زمان در تب‌ها چیست؟ Web Lock فرانت کنترل کمکی است؛ replay و race باید در سرور نیز رفتار مشخص داشته باشند.
5. logout، logout-all، تغییر رمز و بازیابی رمز دقیقاً کدام refresh sessionها و access tokenها را باطل می‌کنند و از چه زمانی؟

### پاسخ دیررس و cookie

فرانت جلوی تغییر حافظه/کش نشست B توسط پاسخ عملیات قدیمی A را می‌گیرد. بااین‌حال، مرورگر می‌تواند `Set-Cookie` پاسخ دیررس را پیش از بررسی JavaScript اعمال کند.

لطفاً مشخص کنید پاسخ دیررس logout/logout-all/password-reset/password-change یا refresh قدیمی چگونه از حذف یا جایگزینی cookie ورود جدید جلوگیری می‌کند. ابطال سمت سرور، خانواده نشست و رفتار header باید مشخص باشند؛ abort کلاینت تضمین rollback سمت سرور نیست.

### معیار پذیرش

- تب A با cache خصوصی A باز باشد؛ پیام خروج قبلی گم شود؛ در تب B ورود جدید انجام شود.
- refresh یا درخواست معلق A دیر برسد؛ هیچ نتیجه A وارد cache/view حساب B نشود.
- حالت از دست‌رفتن تمام اعلان‌ها با هویت قراردادی سرور نیز پوشش داده شود.
- refresh عادی همان حساب بی‌دلیل cache را پاک نکند.
- وضعیت storage/BroadcastChannel ناموجود نیز fail-safe و مستند باشد.

## ۳. cookie، CSRF و CORS در محیط واقعی

لطفاً پیکربندی محیط staging/production را بدون ارسال مقادیر محرمانه تأیید کنید:

- نام و scope cookie: Domain، Path، HttpOnly، Secure و SameSite.
- نحوه CSRF و مجازبودن origin واقعی فرانت؛ رفتار درخواست با credentials.
- expose شدن `X-CSRF-TOKEN` در CORS پاسخ‌هایی که توکن صادر می‌کنند.
- تفاوت تنظیمات localhost/proxy با deployment واقعی.
- status/error code دقیق برای refresh نامعتبر، session revoked، rate limit و خطای موقت.

deadline فعلی refresh فرانت ۱۰ ثانیه و شامل انتظار قفل، CSRF و refresh است. اگر backend SLA یا timeout دیگری دارد، مقدار هماهنگ و retry policy پیشنهادی را اعلام کنید. retry خودکار عملیات غیر idempotent نباید به‌صورت پیش‌فرض فعال شود.

## ۴. قرارداد عملیات پرداخت و کیف پول

برای این endpointها سیاست نتیجه نامعلوم و retry را جداگانه مشخص کنید:

- `POST /api/v1/wallet/charge`
- `POST /api/v1/payment-intents/{intent_uuid}/executions`
- `GET /api/v1/payment-executions/{execution_uuid}`

آیا ساخت intent/execution به کلید idempotency نیاز دارد یا سرور تضمین معادل دارد؟ در صورت قطع پاسخ، کلاینت چه شناسه‌ای را نگه دارد و با کدام endpoint وضعیت را بازیابی کند؟ retry چه زمانی execution جدید مجاز می‌سازد؟

نمونه وضعیت‌های pending، review، financial success با fulfillment ناقص، failure و cancellation و تضمین یکتایی افزایش اعتبار/برداشت را ارائه کنید. صحت callback/webhook و مبلغ/مالیات باید سمت سرور تأیید شود؛ query موفقیت در URL مرجع مالی نیست.

## ۵. بسته fixture مدل‌ها برای CI

fixtureهای مخزن همسایه در این محیط موجود نیستند. وابستگی پنهان به مسیر `../perpix-core-api` حذف شده است؛ تست قرارداد ۱۰ مدل اکنون مسیر artifact را صریحاً از `PERPIX_BACKEND_FIXTURES_DIR` می‌گیرد و در نبود بسته، با خطای روشن متوقف می‌شود. هیچ assertion حذف و هیچ schema ساختگی جایگزین قرارداد واقعی نشده است.

لطفاً بسته JSON قابل انتشار در repo/CI با revision یا SHA-256 مشخص ارائه کنید، شامل:

1. `BLACK_FOREST_LABS_FLUX_1_1_PRO_ULTRA.json`
2. `BYTEDANCE_SEEDANCE_2_0.json`
3. `GOOGLE_GEMINI_OMNI_FLASH.json`
4. `GOOGLE_NANO_BANANA_2.json`
5. `GOOGLE_NANO_BANANA_2_LITE.json`
6. `GOOGLE_VEO_3_1_FAST.json`
7. `IDEOGRAM_4_0.json`
8. `KLINGAI_VIDEO_3_0_STANDARD.json`
9. `OPENAI_IMAGE_2.json`
10. `RUNWAY_ALEPH_2_0.json`

برای هر artifact، نسخه OpenAPI، مدل/provider config، enumها، defaults، شرایط required و نمونه payload معتبر مشخص باشد. مقادیر secret، credential و URL امضاشده واقعی نباید در بسته قرار گیرند. در صورت تفاوت نام یا حذف مدل، تغییر قرارداد باید صریح اعلام شود، نه اینکه تست silently skip شود.

## حداقل خروجی مورد انتظار از تیم بک‌اند

| موضوع | تحویل لازم |
| --- | --- |
| تولید هزینه‌دار | تضمین یا قرارداد idempotency و lookup نتیجه نامعلوم، همراه تست ledger آزمایشی |
| نشست | هویت پایدار حساب/نسل نشست و قواعد rotation، ابطال و cookie دیررس |
| پرداخت | قواعد retry intent/execution، دفتر مالی و callback/webhook |
| تست مدل‌ها | artifact نسخه‌دار fixture و نسخه OpenAPI سازگار |

پس از پاسخ، فرانت فقط قرارداد تأییدشده را پیاده‌سازی و در صورت نیاز API types را از منبع معتبر تولید می‌کند؛ فایل generated به‌صورت دستی تغییر نمی‌کند. پاسخ بک‌اند یا تست ماک به‌تنهایی تأیید انتشار نیست: build کامل، تست‌های حساس با پایان سالم runner و اعتبارسنجی مرورگر همچنان لازم‌اند.
